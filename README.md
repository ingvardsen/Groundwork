# Groundwork

**A Claude Code skill for iterative agent campaigns. Sessions end; the audit trail doesn't**

---

## The problem

Running iterative research or bulk work with AI agents has a hidden flaw: the agent's memory is the conversation. Restart the session, hit the context limit, or hand the work to a different expert, and the thread is gone. You rebuild context from scratch, re-explain decisions, re-discover what was already tried.

Groundwork solves this by making the **filesystem the single source of truth**. Every unit of work is defined in a brief file before it runs, and every outcome is captured in a return file when it completes. The conversation context becomes disposable — the files are not. A new session reads the iteration directory and instantly knows what was done, what was learned, and what comes next.

The same mechanism that makes work resumable makes it **auditable, shareable, and safe to parallelize across expert roles**. A brief is a written contract. A return is a filed report. No verbal context crosses role boundaries.

## Starting a session

### Invoke the skill

In a Claude Code session, either type the slash command:

```
/groundwork-skill
```

Or just describe what you want — Claude will auto-load the skill when it detects a multi-iteration task ("run a sweep across X", "compare A vs B", "audit Z and produce findings").

### What Claude asks at the start

Once the skill is loaded, Claude (as architect) confirms three things before writing the first brief:

1. **Iterations directory** — where brief/return files live (default: `iterations/`)
2. **Category** — shapes the brief template: `audit-sweep` · `comparative-rnd` · `bulk-migration` · `diagnostic`
3. **Resource budget** — default wall-time cap per iteration in seconds

The architect model is whatever your Claude Code session is running. Engineer subagents default to `sonnet` unless a brief's `Model:` field overrides it.

### Resuming an existing campaign

Start a new session, load the skill, and tell Claude the iterations directory. It reads the existing brief/return files and picks up from the last completed slot — no re-explaining context.

### Campaign mode (architect as subagent)

For fully autonomous campaigns where you supervise from outside, spawn an architect subagent and hand it `templates/architect_role.md` as its role:

> "Your role: [paste contents of `templates/architect_role.md`]. Campaign: iterations dir = `iterations/`, category = `diagnostic`, goal = `<one paragraph>`, stop condition = `<when done>`."

The subagent runs the campaign loop and reports back to you for approval after each return.

## How it works

Two roles, one filesystem contract:

- **Architect** (your session) — surveys the iteration directory, authors briefs, gates each iteration on your approval, reads returns from disk, synthesises findings. Does not execute work directly.
- **Engineer** (subagent) — reads one brief, executes one iteration, writes one return. Its verbal response is decorative; the architect reads the file.

```
iterations/
  brief_001_baseline.md       ← architect writes this
  return_001_baseline.md      ← engineer writes this
  001_baseline_work.sh        ← generated by engineer (Pattern B)
  001_baseline_supervisor.sh  ← generated by engineer (Pattern B)
  001_baseline.log            ← live log; Monitor target
  001_baseline.pid            ← supervisor PID
  001_baseline_job.pid        ← work script PID
  synthesis.md                ← architect maintains across iterations
```

Slot numbers are monotonic (`001`, `002`, …). Nothing is ever overwritten.

## Execution patterns

### Pattern A — direct

Single Bash call that completes in under 30 seconds. Engineer runs it inline and writes the return immediately.

Use for: metadata reads, quick analysis, file counts, fast transforms.

### Pattern B — supervised

Work takes longer than 30 seconds or cannot be bounded. The engineer writes a self-contained work script and a supervisor wrapper, launches them detached from its turn, writes a partial return with the PID and log paths, then ends its turn. The OS process runs on independently.

The architect sets up a `Monitor` on the log file and is notified when the terminal sentinel (`DONE` or `FAILED: <reason>`) appears. On `DONE`, a second engineer brief (`Mode: ingest`) reads the completed artefacts and writes the substantive return.

**Sentinel convention:** the supervisor always writes `DONE` or `FAILED: <reason>` as the final log line. The Monitor fires on this. No polling.

**Kill a running job at any time:**
```bash
kill $(cat iterations/NNN_slug_job.pid) 2>/dev/null   # stops the work
kill $(cat iterations/NNN_slug.pid) 2>/dev/null        # stops the supervisor
echo "KILLED by architect" >> iterations/NNN_slug.log
```

## Brief and return schema

Every brief carries these fields:

| Field | Purpose |
|---|---|
| `Intention` | One sentence — what this iteration is trying to learn or change |
| `Hypothesis / target` | Falsifiable outcome or concrete deliverable |
| `Scope fence` | What NOT to do — strict |
| `Expected artefacts` | Files the engineer will produce |
| `Resource budget` | Wall-time cap in seconds |
| `Return trigger` | When to write the return |
| `Mode` | `direct` · `supervised` · `ingest` |

Every return carries:

| Field | Purpose |
|---|---|
| `Status` | `complete` or `partial — <reason>` |
| `Verdict` | One-line answer to the brief's hypothesis |
| `Mechanism / what changed` | The causal *why* — mandatory. A score without mechanism is rejected. |
| `Artefacts` | Files written, with paths |
| `Surprises` | Unexpected findings or forced scope deviations |
| `Resource used` | Actual wall-time |

## Iteration categories

Choose the category when setting up a campaign — it shapes the brief additions:

| Category | Brief additions |
|---|---|
| `audit-sweep` | `Classification taxonomy: [...]` |
| `comparative-rnd` | `Mechanism delta required: yes` · `Refutation outcomes: <...>` |
| `bulk-migration` | `Targets: [...]` · `Per-target acceptance: <...>` |
| `diagnostic` | `Question: <...>` · `Stop criterion: <...>` |

---

## Memory discipline

Do not save iteration state, mechanism findings, or role framings to auto-memory. Push lessons into artefacts — briefs, returns, `synthesis.md`. Auto-memory is for cross-conversation collaboration preferences only.

This is what makes Groundwork restartable: a fresh session reads the iteration directory and has full context without relying on memory.

## Testing

Two test layers ship with the skill. Run both:

```bash
bash tests/run.sh
```

### Layer 1 — infrastructure (`tests/layer1.sh`)

Pure bash, no external dependencies. Verifies the supervisor script lifecycle and slot rule. Runs in ~10 seconds.

Scenarios covered:
- Work script exits 0 → `DONE` sentinel written as last log line
- Work script exits non-zero → `FAILED: work script exited non-zero`
- Work script exceeds wall-time budget → `FAILED: wall-time budget exceeded`
- Kill via `job.pid` → work process is dead
- Empty iterations directory → next slot is `001`
- Mixed existing files → next slot is highest + 1
- Return files count toward slot numbering

### Layer 2 — schema (`tests/layer2.py`)

Requires Python 3 and pytest (`pip install pytest`). Validates the brief and return file contracts against fixture documents. Runs in under 1 second.

Scenarios covered:
- Valid briefs for all three modes (`direct`, `supervised`, `ingest`) pass field checks
- Valid returns (`complete`, `partial`) pass field checks
- Invalid mode values are detected
- Missing required fields are detected
- A complete return without a mechanism is flagged as invalid

Run Layer 2 alone:

```bash
pytest tests/layer2.py -v
```
